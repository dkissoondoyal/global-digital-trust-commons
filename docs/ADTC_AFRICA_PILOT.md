# African Digital Trust Commons (ADTC) — Africa pilot programme

**Relationship:** ADTC is the Africa-focused pilot and community co-design programme of the **Global Digital Trust Commons (GDTC)**. GDTC remains the global open-source technology and governance framework. ADTC is **not a separate legal entity, independent security certification, or second codebase**.

## One commons, complementary responsibilities

| Dimension | GDTC — global commons | ADTC — Africa pilot |
| --- | --- | --- |
| Scope | Shared software architecture, privacy/security expectations, documentation, maintenance and prospective governance | African civil-society needs, usability testing, contextual evaluation, translations and locally relevant recommendations |
| Software | A common source repository and shared security fixes | Regional configuration and test feedback; no fork required at this phase |
| Participants | Prospective global contributors and community representatives | Initially African volunteers, NGOs and civil-society collaborators; other supporters welcome |
| Accountability | Maintainer-led open-source work with future community governance to be developed | Volunteer consent, practical testing, issue reports and documented local learning |
| Languages | Extend according to available contributors and demonstrated demand | English and French initially; further languages subject to community co-design |

**Guiding principle:** *GDTC develops the commons; ADTC tests, adapts and helps shape its usefulness in the African context.*

## Current Africa pilot

The initial experiment is coordinated through IGF Mauritius. Its public source foundation is the bilingual, synthetic-only ADTC v0.1 demonstration. A distinct, controlled GDTC volunteer portal provides individual registration, email verification and coordinator approval. The optional desktop companion and network evidence features are still restricted **internal QA**, not automatically available to all new registrants. Browser-only fictional-data evaluation is sufficient for volunteer participation.

- Request participation: https://igf-mu.org/gdtc-volunteer-register/
- Approved-volunteer login: https://igf-mu.org/gdtc-volunteer-portal/
- Public code, general roadmap and limitations: https://github.com/dkissoondoyal/global-digital-trust-commons
- November 2026 internal acceptance summary: [Read the checkpoint](INTERNAL_ACCEPTANCE_2026-11-10.md)

Registration **requests** may be submitted, but no participant has access until their email is verified and an administrator individually approves the account. Desktop download and active scanning require additional separate authorisation.

Volunteers may test the browser demonstration at their own convenience after approval, without scheduling meetings. They should use fictional data only, avoid sharing organisational secrets or IP details, and report problems privately.

## Separation rules

1. Use **ADTC** when describing the *African volunteer pilot, African NGO requirements and regional feedback*.
2. Use **GDTC** when describing the *global vision, common technology, software repository and eventual shared governance*.
3. Use **GDTC Desktop Companion / Network Evidence Lab** for the common tools, even when used within ADTC, so versions and security documentation do not fragment.
4. Keep one version-controlled software codebase for now; decide on further regional repositories only if there is a concrete governance or maintenance reason.
5. Do not claim African institutional endorsement, partner adoption, completed field validation, Mozilla funding or independent security certification without evidence.

## Proposed volunteer evaluation questions

- Can a non-specialist understand the fictional security observations?
- Do English/French navigation and explanations make sense in African NGO settings?
- Are local privacy expectations and meaningful consent clear?
- Which training, access and connectivity barriers should guide product priorities?
- What should community-led governance, translation and stewardship look like?

## Next stages

- Keep feedback, opt-in records and personal information inside the approved private pilot workflow.
- Complete independent review and clean-machine tests before any broader desktop release.
- Publish version-matched source/build instructions for the deployed companion tools before presenting them as a released open-source version.
- Use anonymised, consented insights to update the shared GDTC roadmap; seek genuine regional partnership rather than assuming it.
